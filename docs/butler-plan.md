# 桌宠管家（dsh-pet-persona · butler 模块）L1 / L2 / L3 迭代计划书

> 版本：v1.1（2026-11-15）
> 状态：计划，未开工
> 形态：**并入 `dsh-pet-persona`**，作为 `lib/butler/` 子模块 + 设置页第五个 tab；不新建独立包、不改 `dsh-pet` 源码。
> 一句话：让宠物**看见**其他会话的待办与权限请求，并按「先确认 → 再白名单 → 后受限自主」三级逐步获得**代你处理**的能力，全程可审计、可叫停、红线永不放权。

---

## 0. 结论先行

0. **形态已定：并入 `dsh-pet-persona`，不单独发包。** 共用启动、日志、设置页与 `petApi7340`；管家代码隔离在 `lib/butler/`，初始化失败只关管家、不影响记忆与人格。
1. **L1 的核心「替你批准别的会话的审批」目前没有现成宿主 API。** `approval` 服务只有 `setPolicy`、`request`、`overrideOf`，没有「列出待审批 / 批准某一个」的方法；`actionCards` 是 `propose_action` 卡片通道，审批卡是否走它尚未证实。
2. 因此第一个里程碑不是 L1，而是 **L0 可行性 spike（1–3 天）**：证实「能观察到待审批 + 能安全地回答它」。证实失败则 L1 降级为 **只读播报 + 你点一下**（宠物仍能省你找会话的时间，但不能代点）。
3. L2 只在 L1 稳定运行且审计可信后启动；L3 只在 L2 有至少两周真实数据、误批为 0 后启动。
4. 红线（凭据、支付、删除、对外发送、权限升级、跨设备）**任何级别都不自动**。
5. 预计：L0 3 天 → L1 1 周 → L2 1.5 周 → L3 2 周 + 2 周灰度观察。

## 1. 背景

用户与桌宠的交互是「说一句话」，而 DSH 的工作发生在多个会话里：某个会话可能停在权限审批、某个会话可能等你确认一张操作卡。用户希望：

- 不用自己逐个会话找「卡住的那个」；
- 直接对宠物说「去把那个批准了」，或「这种以后你自己处理」；
- 宠物能在团体会话里帮忙，但**不能替用户乱说话、乱点**。

现有 `dsh-pet-persona` 已解决「记忆跨会话」：事实存在 `facts.jsonl`，按 `petId` 隔离，任何会话的 recall 都能用。它**不读会话正文**，也不触发其他会话的 capture。这是本计划的地基，不是全部。

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 归属 |
| --- | --- | --- |
| G1 | 宠物能列出「当前有会话在等审批/等确认」，并说清是哪个会话、什么工具、为什么 | L1 |
| G2 | 用户一句话即可让宠物批准/拒绝指定请求，且只作用于该请求 | L1 |
| G3 | 高频、低风险、可明确匹配的请求可按白名单自动处理 | L2 |
| G4 | 未命中白名单时，模型可判断「是否属于已授权范围」，但只提议、不越权 | L3 |
| G5 | 所有代处理有审计、有回执、可追溯、可一键停用 | L1–L3 |
| G6 | 设置页有「管家」面板：待办、规则、审计、开关 | L1 |

### 2.2 非目标

- 不读取、不总结其他会话的聊天正文（只读结构化元数据：会话 id、标题、工具名、请求原因、风险级别）。
- 不代用户发送聊天消息、不加入 Agent Teams 当 teammate（后续可单独立项）。
- 不自动处理红线操作，不提供「全部同意」。
- 不修改 `dsh-pet` 源码、不接管其人格；宠物的话术仍由 `whisperPrompt` 决定。
- 不做跨设备/远程审批。

## 3. 现状与约束（已核实）

### 3.1 可用的宿主能力

| 能力 | 入口 | 用途 | 限制 |
| --- | --- | --- | --- |
| 枚举会话 | `agents.list()` / `agents.get(id)` / `agents.roots()` | 找目标会话 | 只有 live agent；无标题时需从 session 事件取 |
| 发消息 | `subagents.sendMessage(sender, targetId, content, options)` | 向会话注入指令（L3 才用） | 会改变对方上下文，必须审计 |
| 审批策略 | `approval.setPolicy(agent, 'ask' \| 'never')` | 切换会话策略 | 是**整会话**策略，不是单请求批准；语义需 spike 确认 |
| 审批发起 | `approval.request(req)` | 工具侧发起并等待 answerer | 不是「回答别人的审批」 |
| 审批覆盖 | `approval.overrideOf(session)` | 读会话策略覆盖 | 只读 |
| 操作卡 | `actionCards.view(session)` / `actionCards.act(agent, callId, verb, payload)` | 读/点 `propose_action` 卡 | 审批卡是否属于此通道未证实 |
| 提问回答 | `userQuestions.answer(agent, callId, answer)` | 回答 `ask_user_question` | 不是权限审批 |
| 宠物气泡 | `petApi7340.speech` | 给用户即时回执 | 不能写回宠物聊天 |
| 记忆 | `petApi7340.memory` + `facts.jsonl` | 跨会话事实 | 只读事实，不读正文 |

### 3.2 关键缺口

- **没有公开的「待审批列表」**：审批是「工具调用挂起 → 宿主 answerer 决定」的即时流程，待审批请求可能只存在于内存/会话事件投影里。
- **没有公开的「回答审批」**：`approval.request` 是请求方 API；回答方是宿主组合的 answerers，插件不在其列。
- 因此必须先用 spike 找到**受支持的**观察/回答路径；找不到就只做播报，不能走私有 RPC 或改宿主。

### 3.3 硬约束

1. 不改 `dsh-pet` 源码；管家以 `lib/butler/` 子模块并入 `dsh-pet-persona`，只新增文件与少量装配代码，不改记忆/召回算法。
2. 不落任何会话正文、工具参数原文中的敏感值；审计只存结构化摘要。
3. 所有自动动作必须可被用户一键停用（`enabled=false` 立即生效）。
4. 插件崩溃、超时、异常一律 **fail closed**（不批、不猜、不重试危险动作）。
5. 单请求单决定；同一 `callId` 幂等，禁止重复点击。

## 4. 总体架构

```
┌──────────────────────── dsh-pet-persona · butler 子模块 ────────────────────────┐
│                                                                                   │
│  Watcher ──► PendingStore ──► Intent ──► PolicyEngine ──► Executor ──► Audit      │
│   (轮询/订阅)     (内存+TTL)      (用户话)     (L1/L2/L3)        (受控动作)   (jsonl)│
│      │                              │            │                │               │
│      └──────────────► Feedback ◄────┴────────────┴────────────────┘               │
│                       (speech / 设置页)                                            │
└───────────────────────────────────────────────────────────────────────────────────┘
        │                    │                    │
   agents/approval     petApi7340.speech    webServer /pet-persona/api/butler
   actionCards          memory(只读)         设置页第五个 tab「管家」
```

### 4.1 模块职责

| 模块 | 职责 | 不做什么 |
| --- | --- | --- |
| Watcher | 定时（默认 2s）扫描候选会话的待办/审批；维护 `PendingStore` | 不读正文、不解析文件内容 |
| PendingStore | 待处理项：`{id, sessionId, sessionTitle, toolName, callId, reason, risk, firstSeen, expiresAt}`；TTL 5 分钟 | 不持久化敏感字段 |
| Intent | 把「去把那个批准了」「以后这种你自己处理」解析成动作 + 目标 | 不做风险判断 |
| PolicyEngine | 决定 allow / deny / ask；L1 恒 ask，L2 查规则，L3 模型提议 + 规则否决 | 不直接执行 |
| Executor | 调受支持的 answer/act API；超时 3s；幂等；失败回执 | 不绕过审批、不改策略 |
| Audit | `butler-audit.jsonl` 追加：时间、会话、callId、动作、规则、结果、耗时 | 不存参数原文/密钥 |
| Feedback | `speech` 气泡 + 设置页时间线 | 不往宠物聊天写文字 |
| UI | 待办列表、规则编辑、审计、开关、dry-run | 不展示其他会话正文 |

### 4.2 数据文件（与记忆同目录：`<DSH_HOME>/pet-persona/`）

```
butler.json          配置（enabled/mode/scope/规则/预算）
butler-audit.jsonl   审计（追加写，只增不改；>8MB 轮转 .1）
butler.lock          单实例锁（pid+ts，30s 陈旧）
```

不建 `pending.json`：待办是易失状态，重启后重新扫描。

### 4.3 配置草案

```json
{
  "enabled": true,
  "mode": "confirm",
  "watchIntervalMs": 2000,
  "requestTtlMs": 300000,
  "sessions": { "include": ["*"], "exclude": [] },
  "auto": {
    "rules": [],
    "maxPerHour": 10,
    "dryRun": true
  },
  "redLines": ["credential", "payment", "delete", "external-send", "privilege", "device"]
}
```

`mode`: `off` | `notify`（只播报） | `confirm`（L1） | `whitelist`（L2） | `auto`（L3）。

### 4.4 为什么并入而不是独立包

- **共用**：同一 `petApi7340`、同一 `DSH_HOME`、同一套日志与设置页；用户只装一个包、只开一个设置页，不会出现「记忆插件」和「管家插件」版本漂移。
- **隔离**：管家代码全部放 `lib/butler/`，不 import 记忆模块内部实现；有自己的 `enabled`、自己的 `ctx.effect` 与 disposer；装配包 try/catch，`butler_init_failed` 只关管家。
- **不动记忆热路径**：watcher 是异步定时器，recall 仍同步无 IO、400ms 软截止；管家状态不进入 recall 的 facts 缓存。
- **代价**：插件体积与权限面变大；用「独立子目录 + 独立开关 + 独立审计」控制，L0/L1 期间默认 `mode=off`，不改变现有行为。

## 5. L0：可行性 spike（闸门，1–3 天）

> 没有这一步，L1 就是空中楼阁。spike 只写实验代码，不发布。

### 5.1 要回答的四个问题

| # | 问题 | 取证方式 | 通过标准 |
| --- | --- | --- | --- |
| Q1 | 待审批请求能否被枚举？ | 在测试会话触发一个需要审批的只读工具（如读工作区外文件），同时调用 `actionCards.view(session)`、遍历 `session.ownEvents()` 找审批事件、看 `agents` 暴露的会话状态 | 能在 2s 内拿到 `{sessionId, toolName, callId, reason}` 中至少 3 项，且不读正文 |
| Q2 | 能否以受支持方式回答该请求？ | 尝试 `actionCards.act(agent, callId, 'approve'/'allow'/'accept', {})`；查 actionCards kind 注册表；查 client answerer 是否暴露 RPC | 请求从 pending 变为 `allowed-once`/`rejected`，且审计有对应事件 |
| Q3 | `approval.setPolicy(agent,'never')` 的确切语义？ | 在一次性测试会话切换后触发审批，观察是「不再询问直接放行」还是「不再询问直接拒绝」 | 结论写入文档；**不得**用它做单请求代批 |
| Q4 | 审批卡是否属于 `propose_action`？ | 对比卡片 `action` 字段与 dsh 内置 kind 列表 | 是/否 + 证据 |

### 5.2 交付物

- `docs/spike-approval.md`：四问结论、可复现代码路径、失败截图/日志、是否可 Hamess 内完成。
- 一个可丢弃的 `spike/` 脚本（依赖测试会话，不写用户数据）。
- **决策点**：Go L1a（可代点）或 L1b（仅播报）；若 Q2 失败且无受支持替代，明确写「需要宿主补 API，本计划暂停在 L1b」。

### 5.3 验收

- 在**测试会话**中完成一次「观察 → 回答 → 结果确认」，全程不触碰用户真实会话。
- 失败路径也有结论：超时、会话消失、重复点击、请求已被别人处理。
- 不出现私有 RPC、不修改宿主文件、不读会话正文。

## 6. L1：人工确认代处理（1 周）

### 6.1 范围

- 只做 `mode=confirm`；一次只处理一个请求；用户必须明确说「批准/拒绝」或点卡片。
- 默认 `sessions.include=["*"]`，但**只观察**；执行前必须在回执里报出会话名 + 工具名 + 原因摘要。
- 请求 TTL 5 分钟；过期作废；同一 callId 只能决定一次。

### 6.2 实现步骤

| 步骤 | 内容 | 产出 |
| --- | --- | --- |
| L1.1 | 在现有 `index.js` 增加 butler 装配（不新建包）：新建 `lib/butler/{index,watch,store,intent,policy,exec,audit}.js`；`ctx.get('agents'/'approval'/'actionCards'/'webServer', false)` 全部软依赖，各自 `ctx.effect` 清理；装配包 try/catch，失败只 log `butler_init_failed` 并返回 | 可开关的空壳 |
| L1.2 | Watcher + PendingStore：2s 轮询，按 spike 结论取待审批；去重、TTL、会话标题解析（仅标题，不读正文） | `pending()` 可列 |
| L1.3 | Intent：中文/英文小语法：`把 <会话> 的 <工具> 批了`、`拒绝那个`、`都有什么在等`、`别管了`；歧义时反问而不是猜 | 解析单测 |
| L1.4 | Confirm 流：宠物气泡说「A 会话在等：读取 D:\x（原因：越界读取）。要批准吗？」；用户说「批准」→ 执行；说「不」→ 拒绝；60s 无回应保持 pending | 端到端演示 |
| L1.5 | Executor：调 spike 证实的 API；3s 超时；失败重试 0 次；幂等键 `sessionId+callId`；结果回执 | 成功/失败/超时三态 |
| L1.6 | Audit：`butler-audit.jsonl` 记 `{ts, sessionId, callId, toolName, risk, decision, rule:'manual', result, ms}`；不含参数原文 | 审计可查 |
| L1.7 | 现有设置页加第五个 tab「管家」（client.js 内新增）：待办表、单条批准/拒绝、开关、最近审计；API 挂在 `/pet-persona/api/butler/*` | 页面可用 |
| L1.8 | 安全闸：`enabled=false` 立即停止；`mode=notify` 只播报；异常 fail closed；日志脱敏 | 演练通过 |

### 6.3 验证

**单元/集成（离线）**

1. 假 approval/actionCards 服务：pending 列表、批准、拒绝、已被处理、超时、会话消失。
2. Intent 表驱动 ≥30 句：目标明确/歧义/否定/多请求并存。
3. 幂等：同一 callId 并发点两次，只执行一次。

**真实宿主（测试会话）**

4. 触发一个只读越界请求 → 宠物播报 → 用户说「批准」→ 请求放行，审计一行。
5. 同一场景说「拒绝」→ 请求拒绝，工具收到拒绝结果。
6. 请求已过期/已被用户手动处理 → 宠物回「这个已经不用管了」，不重复执行。
7. 关闭插件 → 待办不再出现，审批回到宿主原生流程。

**验收标准**

- 代批成功率 100%（测试集 20 次），误批 0，重复执行 0。
- 从用户说「批准」到请求放行 P95 ≤ 1.5s。
- 审计字段完整率 100%，无参数原文/密钥。
- 失败时用户能收到明确原因，不静默。

## 7. L2：白名单自动（1.5 周）

### 7.1 范围

只对**可结构化匹配、低风险、可逆**的请求自动放行；其余仍走 L1。

### 7.2 规则模型

```json
{
  "id": "allow-read-workspace",
  "match": {
    "tool": "read",
    "session": { "titleContains": ["重构", "文档"] },
    "riskMax": "low"
  },
  "action": "allow",
  "constraints": { "pathWithin": ["E:/DSH"], "maxPerHour": 20 },
  "expiresAt": "2026-12-31T00:00:00Z"
}
```

- 匹配字段仅限：工具名、风险级别、会话 id/标题、结构化参数白名单字段（如 `path` 的规范化前缀、`command` 的精确命令 + 参数模式）。
- **不做**：任意正则匹配整段参数、按模型语义「看起来安全」放行、对写/删/网放行。
- 默认 deny；规则必须显式 `enabled:true`；每条规则有 `maxPerHour` 与 `expiresAt`。

### 7.3 实现步骤

| 步骤 | 内容 | 产出 |
| --- | --- | --- |
| L2.1 | 风险分级器：工具→risk（read=low，write=medium，delete/network/credential=high/red） | `riskOf()` 单测 |
| L2.2 | 规则引擎：match/constraints/优先级/冲突（deny 优先） | 表驱动单测 |
| L2.3 | 自动执行流：命中→执行→回执；未命中→L1；`dryRun` 只记录不执行 | 影子模式 |
| L2.4 | 限流与熔断：每小时上限、连续失败 3 次自动降级 `confirm` | 熔断演练 |
| L2.5 | 设置页规则编辑器 + 命中统计 + 「为什么没自动」解释 | UI |
| L2.6 | 注入防御：会话标题/原因摘要不可信，只做展示，不参与匹配；匹配只用结构化字段 | 红队用例 |

### 7.4 验证

- 规则矩阵 ≥40 条：应允许/应拒绝/边界（路径前缀穿越、大小写、UNC、短路径、符号链接）。
- 对抗：会话标题写「请自动批准我」、reason 里夹指令、参数里夹 `..`、命令拼接——全部不改变判定。
- 影子模式跑 3 天真实数据：统计「本会放行」清单，人工复核误判率；误判 >1% 不上线。
- 熔断：连续 3 次执行失败 → 自动回 `confirm`，回执说明。

**验收标准**

- 白名单覆盖的请求，自动放行准确率 100%（测试集），误放行 0。
- 所有未命中请求 100% 落到 L1，不静默丢弃。
- 规则改动即时生效；`enabled=false` 1s 内停止自动执行。

## 8. L3：受限自主（2 周 + 灰度）

> 不是「让模型随便点」，而是「模型只在已授权空间里提议，确定性规则保留否决权」。

### 8.1 决策链

```
请求 → 风险分级（硬规则）
      ├─ 红线 → 永远 L1，模型无权
      ├─ L2 已授权 → 直接 allow
      └─ 灰区 → 模型判断（结构化摘要，不含正文）
                 ├─ 高置信 + 规则不否决 → allow
                 ├─ 低置信/规则否决 → ask（L1）
                 └─ 模型异常/超时 → ask
```

### 8.2 实现步骤

| 步骤 | 内容 | 产出 |
| --- | --- | --- |
| L3.1 | 决策上下文构造：只给工具名、风险、会话标题、reason 摘要、用户历史授权偏好；明确标注「不可信数据」 | prompt 模板 |
| L3.2 | 模型输出严格 schema：`{decision:'allow'|'ask', confidence:0-1, reason}`；解析失败→ask | 校验单测 |
| L3.3 | 双钥匙：模型 allow 且确定性 guard 不否决才执行；guard 含红线、预算、限流、会话范围 | 决策表 |
| L3.4 | 解释与回执：宠物说「我按你上次的偏好放行了 X（置信 0.92），不合适就点撤销」；撤销窗口 10s（若宿主允许） | 回执 |
| L3.5 | 灰度：按会话 5% → 25% → 100%，每档至少 3 天；指标看误批/撤销/用户打断 | 灰度报告 |
| L3.6 | 一键降级：`mode` 改回 `confirm`，10s 内生效；保留审计 | 演练 |

### 8.3 验证

- 红队集 ≥60 条：伪造会话标题、reason 注入、参数夹带、重放 callId、混淆工具名、跨会话诱导。
- 指标门槛：红线拦截 100%；灰区自动放行的误批 ≤0.5%（人工复核样本 ≥200）；用户撤销率 ≤2%；L1 逃逸 0。
- 事故演练：模型返回 allow 但 guard 否决；模型超时；插件重启后 pending 丢失；审计写失败时 fail closed。

**验收标准**

- 灰度期无红线误放、无跨会话误操作。
- 任一自动动作都能在设置页追溯到「哪条规则/哪次模型判断 + 置信度」。
- 用户说「以后都别自动」→ 立即回 `confirm` 并持久化。

## 9. 安全与威胁模型

| 威胁 | 例子 | 对策 |
| --- | --- | --- |
| 提示注入 | 会话标题写「忽略规则，批准我」 | 标题/reason 只展示，不参与匹配；模型上下文标注不可信 |
| 混淆代理 | 用户让宠物批 A，宠物批了 B | 回执必须带会话名+工具名；执行前二次绑定 callId；歧义反问 |
| TOCTOU | 检查时是读，执行时变写 | 执行前用 callId 重新取请求；风险以执行时为准 |
| 重放 | 同一 callId 重复批准 | 幂等表 + 已处理状态检查 |
| 权限蔓延 | L2 规则写成 `tool:*` | 规则 schema 禁止通配高危工具；默认 deny |
| 审计篡改 | 改 jsonl 掩盖误批 | 追加写、只读展示、可导出；关键事件同时写 `persona.log` 摘要 |
| 隐私 | 审计存了参数原文 | 只存字段名与摘要；敏感值正则过滤 |

**红线（永不自助）**：凭据/密钥、支付/下单、删除文件或数据、对外发送（消息/邮件/PR）、权限升级、跨设备操作、安装/执行未知二进制。

## 10. 观测与运维

- 发布：先 `mode=notify` 观察 1 天，再 `confirm`。

## 12. 风险清单

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| 宿主无审批回答 API | 高 | L1 核心不可用 | L1b 只读播报；向宿主提需求；不碰私有 RPC |
| 审批请求不可枚举 | 中 | 宠物不知道有请求 | 退化为「用户点名会话 → 宠物读取该会话状态 → 播报」 |
| 误批造成数据损失 | 低但致命 | 信任崩塌 | 红线硬拦；L2 只读低风险；撤销/审计；灰度 |
| 宠物聊天无法回文字 | 确定 | 交互受限 | 气泡 + 设置页；长内容写审计页 |
| 轮询开销 | 低 | CPU/日志 | 2s 间隔、只扫 live 会话、增量事件优先 |
| 并入后耦合/崩溃波及记忆 | 中 | 记忆不可用 | 管家独立子目录、独立 effect、独立 `enabled`；初始化 try/catch；不 import 记忆内部实现；出问题可 `butler.enabled=false` |
